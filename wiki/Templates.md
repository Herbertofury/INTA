# 📝 Contribution and review templates

[Home](https://github.com/Herbertofury/INTA/wiki) › [Contribute](https://github.com/Herbertofury/INTA/wiki/Contribute) › **Templates**

Copy the relevant template into a contribution description or review record. Keep customer-specific evidence in the approved private case system and use a generic reproduction here. For an actual service visit, use [Technician Handoff](https://github.com/Herbertofury/INTA/wiki/Technician-Handoff).

## 🛠 Improvement record

| Field | Your entry |
| --- | --- |
| Technician problem | What was difficult, misleading, missing or broken? |
| Affected route | Canonical guide, tool ID, method ID or interface location |
| Expected outcome | What will a technician be able to do after this change? |
| Baseline revision | Exact source commit or existing artifact identity |
| Canonical files changed | Inputs changed; identify generated outputs separately |
| Change | Concrete behavior or knowledge added, corrected or improved |
| Source evidence | Official URLs, applicable dates and material findings |
| Inference or uncertainty | What follows from reasoning rather than direct observation? |
| Tested environment | OS/build, architecture, relevant versions and workload |
| Proof | Test names, actual results and sanitized evidence references |
| Challenge finding | Most material edge case checked and its outcome |
| Compatibility and recovery | Applicable boundary, rollback and residual limitation |
| Publication | Source commit, site, live wiki and complete artifact location |
| Readback | Which published output was opened or retrieved, and what matched? |
| Remaining work | Owner, blocker and literal next action, if any |

### Acceptance checklist

- [ ] The complete affected workflow is usable.
- [ ] Sources support the claims actually made.
- [ ] Every rendered named tool, application and method mention is linked, including repeats.
- [ ] Code and diagram syntax stayed intact; linked legends immediately follow them.
- [ ] Review dates describe real editorial review.
- [ ] Generated outputs match canonical inputs.
- [ ] The relevant checks and real user path were exercised.
- [ ] Required publication and readback succeeded.
- [ ] The source and complete deliverable have recoverable remote copies.

## 🧰 Tool proposal

| Field | What to provide |
| --- | --- |
| Exact product | Official name and stable catalog ID |
| Job fit | The concrete symptom or workflow it helps with |
| Best first use | The narrow first action a technician should take |
| Platforms and mode | Supported environment; portable, installed, boot, web or built-in |
| Official routes | Publisher page, current download route and relevant documentation |
| Operating cost | Installation, privileges, persistent services, resource use and removal path |
| Pricing context | The edition appropriate to professional client work |
| Evidence level | Documentation reviewed, acquired, exercised or compared |
| Tier | Core, specialist or evaluate, with a reason |
| Known boundaries | Coverage gaps, dependencies, compatibility and interpretation limits |
| Promotion test | What must be proven before routine use? |
| Review date | Date the source and applicability were actually reviewed |

Use [the catalog](https://github.com/Herbertofury/INTA/blob/main/data/tools.json) as the exact schema reference. A novel language, large signature count or popular repository is not comparative proof. Use [stable-release promotion](https://github.com/Herbertofury/INTA/wiki/Job-preventive-maintenance) to evaluate a meaningful candidate.

## 🧭 Method or playbook proposal

| Field | What to provide |
| --- | --- |
| Starting condition | What observable situation selects this method? |
| Preconditions | Data, recovery, environment and access requirements |
| Smallest useful kit | Exact tools needed for the selected path |
| Ordered actions | Each action paired with an expected observation |
| Decision branch | What evidence changes the next step? |
| Stop condition | When a technician should preserve state and escalate |
| Acceptance | The original task and neighboring behavior that must pass |
| Evidence retained | Minimal private logs, comparison or recovery evidence |
| Canonical destination | Existing guide or official method documentation |
| Precise aliases | Distinct phrases that cannot be confused with ordinary words |
| Sources | Original documentation supporting capabilities and boundaries |

Register a named concept in [the method registry](https://github.com/Herbertofury/INTA/blob/main/data/methods.json). Add the operational procedure to [the job guides](https://github.com/Herbertofury/INTA/blob/main/data/jobs.json). Avoid duplicating a second procedure under a slightly different name.

Use a [reproducible baseline](https://github.com/Herbertofury/INTA/wiki/Job-slow-pc) and, where initialization matters, a [cold and warm comparison](https://github.com/Herbertofury/INTA/wiki/Job-slow-pc).
